## 9. Known limitations

> Deliberate scope cuts and the fork-updater design write-up. Section numbers (§5, §9, §10) are kept from the original single-file guide so cross-references stay valid.

- **Single account.** `dbVars.userPrefix` names tables per VRChat account and is a mutable global set at login. One server process serves one account.
- **Two settings stores.** `configRepository` (SQLite) moves to the server; `VRCXStorage` (`VRCX.json`) is machine-local and desktop-side. The web client gets a `localStorage`-backed stub (`client-web/shims/vrcx-storage.js`) — not full parity, since a browser tab has no analogue for e.g. window geometry.
- **`AppApi` capability coverage is not exhaustive** in the web client (`client-web/shims/app-api.js`) — everything unimplemented throws (and toasts) "not available in the web client". The remainder is genuinely native-only: VR overlay, Discord RPC, registry, screenshots, `CopyImageToClipboard(path)`. Game launch (`StartGame`/`StartGameFromPath`) is the one exception, found live (2026-08-18): both hand off to the same `vrchat://launch` deep link vrchat.com's own "Launch" button uses (built by the unmodified `src/stores/launch.js`), relying on the OS protocol handler to reach a local VRChat/Steam install — no VRChat autodetection, custom launch arguments, or forced VR/desktop mode, since a browser can pass through only the bare URL. `AssetBundleManager` (`client-web/shims/asset-bundle-manager.js`) is the same story as `LogWatcher`: not part of `AppApi` at all, but reached unconditionally from `checkVRChatCache()` on every world/avatar dialog open, so it's stubbed ("nothing cached") rather than left to throw a bare `ReferenceError`.
- **`speechSynthesis` is a permanent stub everywhere.** The agent channel (phase 5) is request/response, not a fit for routing an ongoing audio stream.
- **One desktop agent at a time.** A second Electron instance connecting to the same server replaces the first agent's connection rather than fanning out to both.
- **No server lifecycle management on the desktop side.** The Electron client never starts a `serve` instance itself ("always external" by design); if one isn't running at all when the client launches, it falls back to `client-desktop/setup.html`. A `serve` *restart* no longer forces this, though — session tokens survive a restart and refresh to stay logged in indefinitely (`server/src/http-auth.js`, `POST /api/session/refresh`).
- **The bundled `.NET`/`node-api-dotnet` footprint hasn't been shrunk.** `AppApiElectron`/`Discord`/`LogWatcher`/`AssetBundleManager`/`AppApiVrElectron` are all real, in-process .NET objects the renderer calls directly; only `SQLite`/`WebApi` were dropped. `.github/workflows/github_actions.yml` (the full, signed release pipeline) is still upstream's own Windows/CefSharp + Azure-signing workflow — its actual *jobs* remain untouched, only its npm→pnpm commands were updated alongside every other workflow in the 2026-08-17 pnpm migration (§5), since letting it silently break was worse than the small diff. `.github/workflows/client-desktop.yaml` (fork-owned, build+smoke-test only, no signing) covers CI verification of the Linux Electron build instead — see also `desktop-release.yaml` (§10) for the real cross-platform, signed release pipeline.
- **The single-writer lock (phase 6) only protects this fork's own processes against each other**, not an old unmodified upstream desktop build opening the same `VRCX.sqlite3` directly. The "don't run both at once" warning in `server/README.md` still applies.
- **Test coverage upstream is thin at the seam.** One test covers ~190 repository methods (`src/services/database/__tests__/gameLog.test.js`). `server/test/db.test.js` is the closest thing to a migration regression test.
- **Node version.** Root `package.json` requires Node ≥24.15; the server itself only needs ≥22.5 (for `node:sqlite` with `setReturnArrays`).
- **The desktop client's built-in self-updater is permanently disabled**, via a new, deliberately empty `.no-updater` file at the repo root (already in `electron-builder.config.js`'s `files` allowlist, so every packaged build bundles it — upstream itself defines this exact marker-file mechanism, `src-electron/main.js`'s `const noUpdater = args.includes('--no-updater') || fs.existsSync(path.join(rootDir, '.no-updater'))`, this fork just never populated it before 2026-08-23). Found live: with no marker file present, the "VRCX Updater" section of Settings was fully active and pointed at `api0.vrcx.app` (`src/shared/constants/settings.js`'s `branches[...].urlLatest`) — upstream's own proprietary release channel, entirely unrelated to this fork's actual releases (GitHub Releases, §10). Left enabled, "Auto Download" would silently fetch and install a genuine upstream VRCX build over a fork install — overwriting the split architecture (native SQLite/WebApi, no headless-server awareness) with no warning. `noUpdater` already gates the whole "VRCX Updater" UI section (`SystemTab.vue`'s `updater_disabled` message) and the update-check calls driven from `initVRCXUpdaterSettings` (`vrcxUpdater.js`), and `isMacOS`/`HEADLESS` were already using the same flag for the same reason; the one gap was the General section's standalone "Latest Version" row, whose `@click="checkForVRCXUpdate"` wasn't gated at all — now also `v-if="!noUpdater"` (that file's own patch-inventory entry). **Deliberately kept disabled rather than repointed at this fork's own releases** — `checkForVRCXUpdate`'s response-shape assumptions (`json.name`/`json.published_at`/`json.assets`, `getAssetOfInterest`) are `api0.vrcx.app`'s own API contract, not GitHub Releases', and `releaseName > currentVersion.value` is a bare string comparison that only orders correctly by luck; a real fork-updater needs its own endpoint (or a GitHub-Releases-shaped adapter) and its own version-comparison logic against this fork's `<vrcx-date>.<minor>.<patch>` scheme, not a quick repoint.

  **(2026-08-24) That fork-updater now exists**, entirely additive — `checkForVRCXUpdate`/`getAssetOfInterest`/`downloadVRCXUpdate`/`branches` above are still completely untouched and still permanently dormant behind `.no-updater`; nothing about this bullet changed. The new flow is server-driven: the desktop client asks its *connected server* for its own version and the matching GitHub release (`server/src/update-release.js`'s `getUpdateInfo()`, a new `update` RPC target in `server/src/rpc.js`), rather than checking "whatever's newest on GitHub" — the server and desktop client are released together under one tag, so a client should track the specific server it's talking to, not drift ahead of or behind it. On a version mismatch with a published release available, the client downloads, SHA256-verifies, and installs **fully automatically** (reusing `Dotnet/Update.cs`'s existing, unmodified download/verify/install machinery via `AppApiElectron.DownloadUpdate`) and relaunches — no confirmation click, per explicit user decision. If the check itself fails (old server without the endpoint, network issue) or no matching release is published yet, it just skips silently rather than looping or crashing — Settings' manual "Retry" (below) is still there for a user who wants to know why. Windows-only at first; extended to Linux on 2026-08-28, see that dated entry below.

  **(2026-08-24, same day) Moved from a post-auth renderer trigger to a pre-auth main-process one.** The first version of this triggered from `src/components/HeadlessServerStatus.vue` (fork-owned) on every "server became reachable" edge, calling the RPC-backed `update` target (`server/src/rpc.js`/`server/src/update-release.js`) via `client-desktop/shims/update-service.js`. Found live: that meant a real, already-in-progress session could get force-closed and relaunched mid-use the moment a mismatch was detected — jarring, and exactly the kind of interruption a background updater shouldn't cause. Fixed by moving the check earlier rather than smoothing over the interruption: `src-electron/main.js`'s `checkAndInstallForkUpdate()` now runs once, in `app.whenReady()`, *before* `createWindow()` — before any window, before `refreshServerSession()`/auth, before the real app or even `client-desktop/setup.html` loads. It talks to a **new, deliberately unauthenticated** `GET /api/update-info` route (`server/src/http-server.js`, reusing `update-release.js`'s `getUpdateInfo()` directly) rather than the authenticated `/api/rpc` `update` target, since there's no session yet — this is the whole point: nothing sensitive is in the response anyway, just this server's own version and GitHub's already-public release metadata. Calls `interopApi.getDotNetObject('AppApiElectron').DownloadUpdate(...)` directly from the main process (the same pattern `ProgramElectron.Init()` already uses nearby), no IPC/renderer round-trip needed. A 5-second `AbortSignal.timeout` bounds the version-check fetch specifically because this now blocks app startup, not just one background check — a hung request here would hang opening the app entirely otherwise. Both "fresh launch" and "server switch" go through this same pre-window code path (`vrcx-switch-server` already restarts the whole process), so removing the renderer-side auto-trigger loses nothing there; the one case it no longer catches is "the connected server was updated while I stayed open the whole time, without ever restarting" — accepted as a gap rather than reintroducing the interrupt. `checkForForkUpdate` stays in `vrcxUpdater.js` as the manual "Retry" action in the "Fork Update" `SettingsGroup` (`SystemTab.vue`, `v-if="isLinux"`, still separate from "VRCX Updater" and its `noUpdater` gate) — the RPC target/`update-service.js` shim it uses are unchanged, just no longer auto-invoked.

  **(2026-08-24, same day) Two follow-up fixes, both found live on real hardware — the first took three attempts.** Relaunch-after-install: `app.relaunch(); app.exit(0)` — relying on `Update.Check()`'s next-boot install, same mechanism the (still-dormant) upstream flow was always going to depend on — silently failed to bring the app back at all. Root cause isn't a race with our own exit: running the pending installer *by hand*, entirely independent of this code path, also left the app closed once it finished — the NSIS one-click installer's own `RUN_AFTER_FINISH` step just doesn't reliably relaunch anything here, reproduced whether the installer runs as a child of this process or not. First fix attempt: spawn `update.exe` ourselves (`getVRCXPath()`-relative path, detached), await its own `'exit'` event, then spawn `process.execPath` (captured before the update, unchanged after — an NSIS one-click install replaces files at the same path rather than moving it) and only then `app.exit(0)`. **That traded it for a different bug**, found live immediately after: the installer's own "VRCX Headless is running, press OK to close it" prompt now blocked on a human, because we'd started it *while our own still-exiting process* (spawned before `app.exit()`, not after) was racing its own "is the app already running" check. Second fix attempt: don't run any of the wait-then-install-then-relaunch chain from inside the exiting process at all — hand it to a detached `cmd.exe /c "timeout /t 3 /nobreak >nul && \"<update.exe>\" && \"<execPath>\""`, which only starts once this process is unambiguously gone. **Still didn't come back** — this time the installer visibly ran (confirming the detached hand-off itself works), but nothing after it did. Root-caused after the fact via the new `apply-update.log` (below): `&&` only proceeds on exit code 0, and this NSIS one-click installer doesn't reliably return one even on a genuinely successful install — the chain just silently stopped one step short of the relaunch, indistinguishable from the app failing to reopen. Real fix: stop gating on exit codes entirely. A generated `apply-update.bat` (not an inline `cmd /c` one-liner — `%errorlevel%` needs somewhere sane to land, and it's easier to read) runs the wait, the installer, and `start "" "<execPath>"` unconditionally in sequence — `start`, not a bare invocation, for that last step specifically so the script (and the detached process running it) doesn't sit around waiting for the freshly-relaunched app to exit before it's allowed to finish. Each step appends a timestamped line to `apply-update.log` alongside the `.bat` (both in `getVRCXPath()`), so a *fourth* failure has a `type` command's worth of diagnosis instead of another guess-and-release cycle. It still didn't come back a fourth time, and `apply-update.log` never got written *at all* — meaning `checkAndInstallForkUpdateInner()` never reached that point, somewhere between the download finishing and writing the batch file. Root cause of finally finding the root cause: every diagnostic in this whole saga had been a bare `console.log()`, which goes nowhere in a packaged app — no attached console, nothing to read. New `logFork()` appends a timestamped line to `fork-update.log` (same directory) instead, called at every branch/return point in `checkAndInstallForkUpdateInner()`, and the exported `checkAndInstallForkUpdate()` wrapper now catches and logs anything the inner function throws — so whatever's still wrong is finally observable without another blind guess.

  Startup splash: the multi-second gap this whole check (and, when found, a real ~130MB download) adds before any window appears had no visible feedback at all — indistinguishable from the app simply failing to launch. New `showSplash()`/`updateSplashStatus()`/`closeSplash()` show a minimal always-on-top window (`client-desktop/splash.html`/`splash.js`, `src-electron/splash-preload.js` — no Vite build needed, same reasoning as `setup.html`) for the duration of `checkAndInstallForkUpdate()`, with live status text including download percentage (polling `AppApiElectron.CheckUpdateProgress()` the same way `vrcxUpdater.js`'s `downloadFileProgress()` already does for the dormant upstream flow).

  **(2026-08-28) Extended to Linux, verified live end-to-end.** `checkAndInstallForkUpdateInner()`'s asset-suffix logic now branches on `process.platform`: `win-${arch}.exe` on Windows as before, `${arch}.AppImage` on Linux — matching `build-scripts/rename-builds.js`'s real artifact naming (`VRCX-Headless_<version>_<arch>.AppImage`) — gated on `appImagePath` actually being set (a dev/unpackaged Linux run has nothing to self-update, same reasoning `installVRCX()`'s own guard already uses). `getForkAssetOfInterest` in `src/stores/vrcxUpdater.js` (the renderer's manual "Retry" path) got the matching fix, picking the suffix off `navigator.platform` (the real host OS, same check `SystemTab.vue`'s `isRealLinux` already uses — `LINUX` here only means "this is the Electron build," not the host OS) rather than assuming Windows; its own install/relaunch path needed no change, since `restartVRCX()` → `restartApp()`'s existing Linux branch already understood AppImage restarts. One real wiring gap: `Update.Init(appImagePath)` — which tells `Dotnet/Update.cs`'s `DownloadUpdate` to take its AppImage-swap branch instead of writing a Windows-style `update.exe` — is normally called by `installVRCX()`, which runs *after* `checkAndInstallForkUpdate()` in `app.whenReady()`; the pre-window updater now calls it itself before downloading (harmless to call twice, the state is static on the .NET side).

  Verified live against the real, already-published `v20260718.24.0` GitHub release (a genuine mismatch in a dev/unpackaged build, whose `app.getVersion()` never matches the fork's `<date>.<minor>.<patch>` scheme) — real download, real SHA256 verification, real in-place AppImage swap, confirmed via `fork-update.log` and the swapped file's presence on disk. That first live run surfaced two real bugs, neither hypothetical:

  1. **`app.exit()` does not stop the calling `app.whenReady().then(async () => {...})` chain from continuing.** The Linux branch originally ended the same way the Windows one always has — `app.exit(0)` as the last statement, trusting the process would already be gone by the time anything else ran. It isn't: `await checkAndInstallForkUpdate()`'s continuation ran `createWindow()`/`createTray()`/`installVRCX()` anyway, confirmed live by "Creating main window" appearing in the log *after* "Download + hash check complete" — spinning up a real GPU-accelerated window (and tray, and native init) for a process already mid-exit. This is presumably a latent bug in the pre-existing Windows path too (untested there — no live Windows box for this session), not something the Linux work introduced. Fixed at the root rather than patched per-platform: `checkAndInstallForkUpdateInner()` now returns `true` whenever it already called `app.exit()` (both platforms), and the `app.whenReady()` handler skips `createWindow()`/`createTray()`/`installVRCX()` entirely when it does.
  2. **`app.relaunch()`'s scheduled spawn silently never fires if the process dies via `SIGKILL` instead of Electron's own graceful quit sequence.** The first version of the Linux relaunch used `app.relaunch({execPath: appImagePath}) + app.exit(0)`, mirroring `restartApp()`'s existing Linux branch. Bug (1) above meant `createWindow()` ran regardless, and tearing down that freshly-created window hung on exit on this Wayland session — `scheduleForceExitFallback()`'s watchdog had to `SIGKILL` the process 3s later, exactly the scenario it was built for. But `app.relaunch()` only actually spawns its registered command as a side effect of Electron's *own* quit sequence completing; a raw `SIGKILL` bypasses that entirely, and the relaunch silently never happened — confirmed live: the AppImage was correctly swapped in place on disk, but no new process ever started. Fixing (1) alone would have made this moot (a window-free exit shouldn't hang), but relying on `app.relaunch()` post-`scheduleForceExitFallback()` is fragile by construction wherever a watchdog-forced kill is even possible — the exact same pattern is still present, unverified, in `restartApp()`'s own Linux branch. Replaced with a direct detached spawn instead, the same pattern `tryRelaunchWithArgs()` above already uses for its own Wayland-relaunch case: `spawn('sh', ['-c', 'sleep "$1"; exec "$2"', 'relaunch', delaySeconds, appImagePath], {detached: true})`, spawned *before* `app.exit()` so it exists independent of however (or whether) this process's own exit completes. The shell's own sleep (5s) is deliberately longer than `scheduleForceExitFallback()`'s 3s kill delay, so the old process — killed cleanly or forcibly — is guaranteed dead before the real relaunch attempt, avoiding a bounce off `requestSingleInstanceLock()`. No argv carried over to the relaunched process (unlike `restartApp()`) — it goes through its own normal cold start, including its own `tryRelaunchWithArgs()` call, exactly like a user double-clicking the AppImage.

  Re-run after both fixes: no window created pre-exit, watchdog still had to `SIGKILL` (a splash-window-only Wayland teardown hang, unrelated to either bug above and out of scope here), and ~7s later a fresh process came up already reporting the swapped-in version, confirming the whole loop closed correctly with no further update attempted.

  **(2026-08-28, later the same day) Two more issues, found from the user actually running it rather than the sandboxed test above.** First: the freshly-relaunched process still hit `installVRCX()`'s pre-existing "install to `~/Applications`?" `dialog.showMessageBoxSync` prompt — a blocking, synchronous dialog appearing right after a supposedly silent background update, contradicting the fork-updater's own "no confirmation click, ever" design principle. Fixed with a new `postUpdate` flag (`args.includes('--post-update')`, defined beside `noUpdater` and friends near the top of the file) carried on the relaunch spawn and checked in `installVRCX()`'s dialog guard (`!hasAskedToMoveAppImage && !postUpdate && ...`) — skipped for this one run only, not persisted to `VRCXStorage`, so an ordinary later launch (a real double-click) still asks if the question was never actually answered. Second, reported directly ("I accidentally relaunched the app twice"): carrying only `--post-update` on the relaunch meant the fresh process's own `tryRelaunchWithArgs()` (the pre-existing Wayland/ozone fix) saw no `--ozone-platform-hint=auto` in its argv and relaunched *itself* a second time — stacking a second, immediate relaunch right after this one's already-5s-delayed one, visibly restarting the app twice for a single update. Fixed by having the update relaunch itself carry the same flags `tryRelaunchWithArgs()` would have added (`--appimage-extract-and-run`, `--ozone-platform-hint=auto` unless `x11`) so the fresh process's own guard already finds itself satisfied and never re-relaunches — collapsing it back to one relaunch, verified live via the process tree showing a single AppImage-wrapper→extracted-binary hop instead of the earlier wrapper→binary→self-relaunched-binary chain.

  **(2026-08-28, later still) Hash verification hardened to fail closed instead of fail open.** `Dotnet/Update.cs`'s `DownloadUpdate` (unmodified upstream) already SHA256-verifies the download when given a hash — but if the hash string is empty, it just logs "skipping hash check" and installs anyway. Both callers (`checkAndInstallForkUpdateInner()` here and `getForkAssetOfInterest()`/`installForkUpdate()` in `vrcxUpdater.js`) derived that hash from GitHub's `asset.digest` with a bare `?.startsWith('sha256:') ? slice(7) : ''` — meaning if GitHub ever changed its digest algorithm, stopped populating it, or returned a malformed value, the hash would silently come out empty and the update would install *unverified*, indistinguishable from a routine "nothing to update" in the log. New shared-by-name `parseSha256Digest(digest, assetName)` (independently defined in both files — plain CommonJS here, ESM store there, no shared module boundary to put one copy behind) validates the full `sha256:<64 lowercase hex chars>` shape via regex and **throws**, rather than falling back to an empty string, on anything else. The throw is deliberate, not a stricter return-null: a `.find()`-style "no match" reads as routine and would hide a real integrity problem behind the same "nothing to report" path as a normal platform mismatch — this needs to look different. Threaded through both callers' existing `catch` blocks (`checkAndInstallForkUpdateInner()`'s already-existing try/catch around `DownloadUpdate`; `installForkUpdate()`'s asset lookup moved *inside* its own try so the throw lands there instead of escaping uncaught) so it surfaces as a specific, readable failure through the same error-reporting path an actual download failure already uses, not a new one. Covered by a new test (`src/stores/__tests__/vrcxUpdater.test.js`) asserting a non-sha256 digest refuses to call `DownloadUpdate` at all.

  **(2026-08-25) Versioning scheme split into real MINOR/PATCH, and `getUpdateInfo()` changed with it.** Every release before this point used a single fork-build counter always followed by a hardcoded `.0` — no PATCH release ever actually existed, so "the client's update target matches the server's exact version" and "the client's update target matches the server's MINOR" were indistinguishable. Per explicit design decision, MINOR now means "needs this server redeployed" and PATCH means "client-only, no redeploy needed" (§10's "Server/Docker versioning" has the full split and the updated "Cutting a release" steps). That makes an *exact*-version match wrong on its own terms: a client-only PATCH release, by definition, ships with the server left exactly as it was, so a real running server can legitimately be several PATCHes behind the newest one published under its own MINOR — and a client stuck waiting for an exact match would never see those PATCHes at all until someone redeployed the server for an unrelated reason. `update-release.js`'s `getUpdateInfo()` now lists releases (`GET /repos/.../releases`) instead of looking up one exact tag, and picks the highest PATCH whose tag starts with the server's own `<major>.<minor>.` prefix — same "nothing published yet" fallback behavior as before, just matched on prefix instead of full equality. `server/VERSION` changed shape too, from a bare integer to `<minor>.<patch>`; `readForkVersion()`'s callers were already centralized enough (`buildServerVersion()`, `build-scripts/utils.js`'s independent `getForkVersion()` re-derivation, the two workflow YAML version-computation steps) that dropping the hardcoded `.0` suffix at each of those call sites was the entire migration — no `src/**`/client-side code needed to change at all, since it only ever sees the fully-joined version string, never `server/VERSION`'s raw contents.

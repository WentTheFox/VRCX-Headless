## 10. The container

> Container, versioning, release cutting and desktop release artifacts. Section numbers (§5, §9, §10) are kept from the original single-file guide so cross-references stay valid.

`server/Dockerfile` (build context is the **repo root**, not `server/`), published by `.github/workflows/server-docker.yaml` to `ghcr.io/<owner>/vrcx-headless-server` for `linux/amd64` and `linux/arm64`. User-facing docs: `server/README.md`.

**Design notes:** the image installs `server/package.json`, not the root manifest — the root keeps everything in `devDependencies`, while the image layout (`/app/{node_modules,src,server}`) mirrors a dev checkout so Node resolves `src/**`'s bare imports upward exactly as locally. Dependency versions are stated twice as a result, checked by `server/scripts/check-deps.js` in CI. Every dependency is pure JS (`node:sqlite` is built into the Node binary), so Alpine/musl is safe and the arm64 build under QEMU is cheap. A third, discarded build stage runs `pnpm run prod-web` to produce the bundled web client under `build/html-web`, pinned to `--platform=$BUILDPLATFORM` so the multi-arch CI build produces it once, not once per target arch. CI builds the native-arch image, smoke-tests it (`migrate --create`, `--help`, and a real `serve` boot checking both `GET /` and `/api/*` routing) before publishing.

### Server/Docker versioning

**The release version is real semver with the VRCX base as the major component**: `<vrcx-date-no-dots>.<minor>.<patch>` — e.g. `20260718.1.0` for the first fork release built against VRCX 2026.07.18. The VRCX version is the version, not a footnote buried in build metadata (an earlier iteration of this scheme did exactly that, `<fork>+vrcx.<vrcx>`, and got corrected before it ever shipped for burying the one thing this was supposed to surface).

**MINOR and PATCH mean something specific, not just "two counters"** (changed 2026-08-25 from a single always-`.0` fork-build counter): MINOR bumps on any change that needs **this server container itself redeployed/restarted** to take effect — `server/**`, the shared `src/services/**` data layer, a DB schema/migration change, anything that changes what the server actually does or serves. PATCH bumps on a **client-only** change — desktop/web UI, `src-electron/**`, `client-desktop/**`, `Dotnet/AppApi/Electron/**` — that needs no server change at all, and resets to `0` on the next MINOR bump. This distinction is what the desktop auto-updater (§9's fork-updater write-up) actually relies on: see "Desktop client version matching" below. Deciding which one a given change is is a judgment call at release-cut time, not something derivable mechanically — when in doubt, a MINOR bump is always safe (it just means an unnecessary redeploy), a PATCH bump for something that actually touched the server is not.

Two source files, two different reasons to change:

- **`server/VERSION`** — this fork's own release counter, now `<minor>.<patch>` (e.g. `20.3`), not a bare integer. Bumped on every server/Docker release that's worth tagging, per the MINOR/PATCH rule above; **reset to `1.0` on every upstream sync** (§6), since a new VRCX base restarts the count. `server/src/globals.js`'s `readForkVersion()` reads it; `readForkMinorVersion(forkVersion)` pulls out just the MINOR half, for the auto-updater's "same MINOR, any PATCH" matching below.
- **`Version`** (repo root, existing, untouched) — upstream's own date tag, already the source of truth for the Electron client's version stamp and the real VRChat user-agent string (`readVersion()` — do not repurpose that function for this).

`buildServerVersion(forkVersion, vrcxVersion)` (`server/src/globals.js`) combines them — strips `Version`'s dots (`2026.07.18` → `20260718`) and joins as `<that>.<forkVersion>`, where `forkVersion` already carries both the MINOR and PATCH components. Safe as a bare semver major with no leading-zero problem for the foreseeable future (the leading digit is the year's own leading digit, non-zero until year 10000), and — being fixed-width `YYYYMMDD` — it also sorts correctly as a plain integer across dates, so nothing downstream needs real semver-aware comparison to get "which is newer" right. Printed by `pnpm run server -- info` (`server version` line, alongside the dotted `Version` for readability) and baked into the image as the `org.opencontainers.image.version` label (`server/Dockerfile`'s `SERVER_VERSION` build `ARG`, computed the same way in `.github/workflows/server-docker.yaml`'s `version` step — shell `tr -d '.'` mirroring the JS `replaceAll('.', '')`).

**Release trigger is a git tag, deliberately** — `git tag v<vrcx-no-dots>.<minor>.<patch> && git push --tags` is what publishes the immutable, pinned Docker tags: this reuses the workflow's existing `on.push.tags: ['v*']` trigger and `docker/metadata-action`'s `type=semver` patterns as-is, no custom tag-generation logic needed since the version *is* real semver now. Every ordinary push to `main` (tagged or not) still publishes/updates the floating tags below. A PATCH-only (client-only) release still gets a real tag and still runs both this workflow and `desktop-release.yaml` — the server code hasn't changed, so the resulting image is content-identical to the previous MINOR's, just republished under the new tag; nobody has to actually redeploy it as a result of that tag existing.

Resulting Docker tags on `ghcr.io/<owner>/vrcx-headless-server`:

| Tag | Meaning | Updates on |
|---|---|---|
| `20260718.1.0` (`{{version}}`) | Immutable pin to one exact fork release | a matching tag push only |
| `20260718.1` (`{{major}}.{{minor}}`) | Floating latest PATCH under that MINOR — genuinely moves now on every client-only release, not just a theoretical hotfix case | a matching tag push only |
| `20260718` (`{{major}}`) | Floating "latest fork build against this VRCX base" — what a `vrcx-<date>` bespoke tag would have been, gotten for free from semver instead | any tag push sharing that major |
| `latest` | Floating absolute latest | a tag push only |
| `main`, `sha-<short>` | Dev builds | every push to `main` |

#### Desktop client version matching

The desktop auto-updater (`server/src/update-release.js`'s `getUpdateInfo()`, §9's fork-updater write-up) does **not** look for a release matching the server's exact version — it lists this fork's GitHub releases and offers the client the highest PATCH published under the server's own `<major>.<minor>`, even if that's newer than what the server itself reports. That's deliberate, not a bug: a PATCH release never required the server to be redeployed, so a real, still-running server can correctly be several PATCHes behind the newest one available for its own MINOR. A MINOR mismatch is unaffected by this — that still only happens when the server container itself was actually rebuilt, and the client still just re-checks against whatever MINOR the new server reports.

#### Cutting a release

1. `cat server/VERSION` (now `<minor>.<patch>`) — decide MINOR vs PATCH per the rule above, then:
   - **New upstream sync** (§6): set it to `1.0`.
   - **Server-requiring change (MINOR bump):** increment the first number, reset the second to `0` — e.g. `20.3` → `21.0`.
   - **Client-only change (PATCH bump):** increment only the second number — e.g. `20.3` → `20.4`.
2. Compute the tag: `echo "v$(cat Version | tr -d '.').$(cat server/VERSION)"` — e.g. `v20260718.21.0` or `v20260718.20.4`.
3. Commit the `server/VERSION` bump on `main` first, then tag *that* commit and push both:
   ```bash
   git tag -a v20260718.21.0 -m "..."
   git push origin v20260718.21.0
   ```
4. Watch it: `gh run list --workflow=server-docker.yaml` / `gh run watch <run-id>` — the same job that runs on every `main` push (tests, build, smoke tests) runs again for the tag push, then publishes the tags above.
5. If a tag push fails before the publish step (nothing was pushed to GHCR under it — verify via the run log, not by assumption), it's safe to fix forward and move the tag: `git tag -d vX.Y.Z && git push origin :refs/tags/vX.Y.Z`, fix, re-tag, re-push. Once a tag push has actually reached the publish step, treat it as immutable instead — cut a new release rather than moving it.
6. The same tag push also triggers `.github/workflows/desktop-release.yaml` (below) — watch it the same way, `gh run list --workflow=desktop-release.yaml`.
7. **A PATCH-only release needs no server redeploy** — the operator running the previous MINOR's container can leave it exactly as-is; connected desktop clients pick up the new PATCH on their own next connect/switch (see "Desktop client version matching" above). Only a MINOR bump needs the container itself updated (`server/README.md`'s "Desktop client auto-updates").

#### Desktop client release artifacts

The same `v*` tag that cuts a Docker release also triggers **`.github/workflows/desktop-release.yaml`**: Windows and Linux build a full x64+arm64 matrix (`build` job, 4 legs, self-signed on Windows), macOS builds Apple Silicon only and ships **unsigned** (`build-macos` job, 1 leg), and all 5 artifacts — `VRCX-Headless_<fork-version>_<arch>.{AppImage,dmg}` for Linux/macOS, `VRCX_Headless_<fork-version>_Setup_<arch> (win-<arch>).exe` for Windows, where `<fork-version>` is the same `buildServerVersion()` scheme as the Docker tag (§10's "Server/Docker versioning") — attach to a GitHub Release for that tag, **published immediately**. Windows uses a native-arm64 runner (`windows-11-arm`) rather than cross-compiling, for the same reason macOS uses a native Apple Silicon runner: `node-api-dotnet`'s prebuilt native binary must match the *target* arch, and `pnpm install`'s normal optionalDependency resolution only gets that right when it runs on a matching host.

**Published immediately, not draft, as of 2026-09-06.** This repo has GitHub's "Immutable releases" setting active — once a release is *published*, its assets can never be edited or replaced — so every release through that date was created as a **draft** instead, requiring a human to check the artifacts and publish by hand from the GitHub UI. That safety net existed for the pipeline's first several releases (new cross-platform RIDs, self-signed certs, an unverified macOS build); once enough real releases passed through it without the manual check ever catching anything, per explicit user decision it was switched to immediate-publish (`.github/workflows/desktop-release.yaml`'s `publish-release` job, `gh release create` with no `--draft`). If a future signing/artifact change needs that safety net again, reintroduce `--draft` there — see git history for the exact flag. (This also happens to sidestep a GitHub Actions quirk worth knowing about: a `release: published` event created by the default `GITHUB_TOKEN` — as this `gh release create` step does — does **not** trigger other workflows watching for it, unlike a human clicking Publish in the UI. That mattered while `aur-publish.yaml` existed, gated on exactly that event; it doesn't matter now that that workflow is gone — see "No AUR package" below — but a future `release`-triggered workflow added here would need a PAT instead of `github.token`, or a `workflow_run` trigger, to actually fire.)

**Signing setup (one-time, per machine that will hold the secret):** run `build-scripts/generate-self-signed-certs.sh` locally to produce `codesign-windows.pfx` — a self-signed Windows Authenticode cert, `CN=WentTheFox, C=HU, ST=Pest, L=Budapest`, empty passphrase. Base64-encode it and set one GitHub Actions secret: `WIN_CSC_LINK`. No `WIN_CSC_KEY_PASSWORD` secret — Windows signing works correctly with that variable left unset. Self-signed means it reduces some SmartScreen friction (a real signature is present) but does **not** eliminate the "unidentified developer" warning. The `.pfx` file never gets committed — `.gitignore` blocks it by extension — and contains private key material regardless of the empty passphrase, so keep it off anywhere less trusted than the machine that generated it.

**`.NET` RIDs:** since upstream's 2026-09 consolidation there is one project, `Dotnet/VRCX-Electron.csproj`, for every OS/arch. The fork only adds `win-arm64` to its `<RuntimeIdentifiers>`. Output goes to `build/Electron/<rid>/`, which `electron-builder.config.js` packages from. Every `desktop-release.yaml` leg passes an explicit `-r <rid>`. `<DefineConstants>LINUX</DefineConstants>` is untouched. That define is the "this is an Electron build" flag (`Dotnet/Program.cs`'s `#if LINUX` around the entire `ProgramElectron` class), not an OS flag, and must stay set for every RID including Windows/macOS (§1's "Build flags are not OS flags").

**macOS is Apple Silicon only and ships unsigned, both permanent, not open items.** `macos-x64`/`macos-13` runners never reliably dispatch on this account (confirmed not a billing/plan gate, the repo is public) — retry rather than assume a workflow bug if a real release stalls on the macOS leg. Unsigned is a harder limitation: a self-signed PKCS12 can be imported into a macOS keychain (needs explicit `-certpbe PBE-SHA1-3DES -keypbe PBE-SHA1-3DES -macalg SHA1` on export, since OpenSSL 3.x's modern default encryption fails macOS's `security import` regardless of password), but electron-builder's own identity-discovery preflight then refuses to use it anyway — macOS flags any cert with no trusted CA chain as `CSSMERR_TP_NOT_TRUSTED`, which every self-signed cert always is, and electron-builder has no config option to override that check. A real fix means bypassing its built-in mac signing entirely (manual keychain trust + direct `codesign`) — out of scope. `build-scripts/generate-self-signed-certs.sh` only generates the Windows cert; there's nothing for macOS to sign.

`Dotnet/AppApi/Electron/**` still has zero macOS branching regardless of signing — folder ops, VRChat autodetect/launch, and overlay remain expected-broken on macOS until someone does for it what `GameHandler.cs` already got for Windows.

#### No AUR package

An `aur/vrcx-headless-bin/` PKGBUILD plus an `aur-publish.yaml` workflow existed briefly (built 2026-08-18–2026-08-25) to publish a `vrcx-headless-bin` package wrapping the released x64 AppImage, gated on an `AUR_SSH_PRIVATE_KEY` secret tied to a real AUR (aur.archlinux.org) account. Removed 2026-09-06 — that account was never actually registerable, so it was dead weight rather than dormant-until-someone-does-it: every `aur-publish.yaml` run through `v20260718.26.0` logged `AUR_SSH_PRIVATE_KEY is not set -- skipping publish` and exited successfully, meaning nothing was ever actually pushed to AUR despite the green checkmarks. If AUR distribution is wanted again later, git history before this commit has the working PKGBUILD/workflow to resurrect rather than rebuilding from scratch.
